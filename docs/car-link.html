Cable to Channel

What happens between plugging an Ethernet cable into the car and a number landing in the database. Nine stages, the actual bytes on the wire, and the YAML that decides all of it — because in this project vehicle knowledge is data, not code.

link-local · UDP discovery HSFZ over TCP capability probing mapping resolution the poll loop SQLite · dashboard · ClickHouse
1

Get an address nobody assigned

live.py · find_link_local_ip()

The car's gateway has no DHCP server. Both ends self-assign from the link-local range 169.254.0.0/16 — the same mechanism a laptop uses when it plugs into a switch with nothing on it.

So before anything can be sent, the host needs a 169.254.x.x address on the cable interface. On a laptop the OS does this automatically; on the Raspberry Pi it has to be configured. Without it, every later stage fails with no route to host.

Failure mode worth knowing: if the interface came up with only a regular DHCP address, discovery in stage 2 broadcasts into the wrong subnet and simply times out. It looks like the car is off.
2

Shout into the dark

live.py · discover() · UDP :6811

We do not know the gateway's address — that is the whole point. So we broadcast six bytes to everyone on the segment and wait for whoever answers.

UDP broadcast → 169.254.255.255:6811 sent once, at startup
identify request 00 00 00 00 00 11

Four zero length bytes, then control word 0x0011 — "who is out there?"

The ZGW — the car's central gateway — replies from its real address. Two things come back: the IP we will talk to, and the VIN, which the gateway volunteers in the payload whether we want it or not.

This is the only UDP in the whole system, and it happens exactly once. Everything after it is one TCP connection. Passing --ip skips this stage entirely.
3

Open the one connection

live.py · HsfzClient.connect() · TCP :6801

Port 6801 is fixed — nothing was negotiated in stage 2, we only learned an address. This single socket now carries every request for the rest of the drive.

The protocol is HSFZ (BMW's "high-speed data interface"): a four-byte length, a two-byte control word, then the payload. The first two payload bytes are the source and destination ECU addresses — this is how one socket reaches many control units.

Request — read engine RPM from the DDE HSFZ frame, 10 bytes total
length 00 00 00 04
control 00 01
src → dst F4 12
payload · OBD mode 01, PID 0x0C 01 0C

F4 = tester (us) · 12 = engine ECU · control 0x0001 = diagnostic request

Response 0x41 = 0x01 + 0x40, the positive-reply convention
length 00 00 00 06
control 00 02
src → dst 12 F4
payload · echo + two data bytes 41 0C 0C 3C

0x0C3C = 3132 → ÷ 4 = 783 rpm. The divisor comes from the mapping, not from code.

ControlMeaningWhat we do
0x0001diagnostic requestwhat we send
0x0002positive responsedecode it
0x0003 / 0x0043not routable — nobody at that addresscount a fault, keep the link
0x0040 / 0x0041gateway alive-checkanswer it, keep waiting
The ZGW serves one client at a time. A second tool on the same cable shows up as a connection reset, not a polite refusal — which is why the runbook says stop live.py before running anything else.
4

Ask who is home

live.py · discover_ecus() · bmwdiag/obd/capability.py

We never assume an address means an ECU. The engine control unit is whichever ECU answers PID 0x0C — engine speed. If BMW moved it, or the same code ran on a different car, nothing would need editing.

Each responding ECU also publishes a support bitmask: the list of PIDs it admits to answering. On this car that comes back as 30 PIDs. That list becomes a filter in the next stage.

Proprietary channels need a second, stricter probe. Rather than trusting an identification string, we replay a read the mapping nominates and see whether the ECU answers it in the declared shape. That proves compatibility with a family of reads — it is what activates the mapping — and nothing more: which exact SGBD revision the ECU is stays unknown until identity evidence says otherwise, and on this car the ident DIDs refuse.

What comes out of stage 4
  • engine addr0x12 — because it answered 0x0C, not because it is 0x12
  • supported PIDsthe 30-entry set this ECU advertises
  • profilefseries-f303-d72-compatible: compatible, because a nominated read answered — with the reason for every probe that did not
  • exact SGBDunknown — no identity evidence; the rows were derived from d72n47a0, which is provenance, not identity
5

What a mapping file actually says

mappings/**/*.yaml · parsed by bmwdiag/mapping/loader.py

Here is the whole idea. live.py does not know what engine RPM is. It knows how to send bytes and how to follow instructions. The instructions are these files.

mappings/candidates/bmw/egs/f10_transmission.yaml abridged 
# ---- identity ------------------------------------------
mapping:
  id: candidate-f10-egs-transmission
  version: 4          # stamped on every sample
  production: false   # opt-in only, via --extra-mappings

# ---- where the knowledge came from ---------------------
source:
  type: manual
  notes: OBDb/BMW-5-Series @ 9c5aa60 (CC-BY-SA-4.0)

# ---- what has been proven ON THIS CAR ------------------
verification:
  status: verified
  method: road drive 2026-08-27 — byte 1 steps 1..8 with speed

# ---- which ECU answers ---------------------------------
ecu:
  family: transmission
  target: 0x18

# ---- how often ------------------------------------------
polling_classes:
  egs: {seconds: 0.5, priority: 4}

# ---- what to send ---------------------------------------
requests:
  egs.selector.DA2E:
    did: 0xDA2E              # UDS service 0x22, read this
    polling: {class: egs}
    response: {data_length: 2}

    # ---- what comes back — TWO channels, ONE exchange ----
    signals:
      egs_da2e_b0:
        decode: {type: uint8, offset: 0}
        log: false          # constant on this car: show, don't store
      gear:
        label: Gear
        decode: {type: uint8, offset: 1,
                 valid_min: 1, valid_max: 8}
  • requestsone exchange with the ECU. This is the unit that gets scheduled.
  • signalsthe channels decoded from that one reply. Two here — so adding a second channel cost no extra traffic at all.
  • did: 0xDA2Ea manufacturer-defined address. Means engaged gear on this ECU and something else entirely on another make.
  • decodea fixed vocabulary of arithmetic steps — no expression language. Nothing in these files ever executes.

Standard OBD looks the same but simpler, because the definitions are public. This is the only file the default launch loads:

mappings/obd/engine.yaml SAE J1979 — no proprietary knowledge 
ecu:
  target: discovered_engine   # a NAME, never an address
  match:
    capability:
      obd_mode01_pid: 0x0C   # "whoever answers RPM is the engine"

polling_classes:
  # ONE unit: seconds of wall clock. Nothing else.
  motion:  {seconds: 0.1, priority: 0}
  context: {seconds: 10,  priority: 1}
  slow:    {seconds: 10,  priority: 2}
  rare:    {seconds: 60,  priority: 3}

requests:
  obd.mode01.0C:
    pid: 0x0C
    polling: {class: motion}
    response: {data_length: 2}
    signals:
      rpm:
        label: Engine speed
        unit: rpm
        decode: {type: uint16_be, divide: 4.0}

# computed from other channels, never read from an ECU
derived:
  boost:
    operation: subtract_scale
    inputs: {value: map, reference: baro}
    fallback: {reference: 100.0}  # baro is only read once a minute
    divide: 100.0
  • discovered_enginea late-bound placeholder. Stage 6 substitutes the address that actually answered.
  • derivedchannels computed from other channels. boost = (map − baro) ÷ 100, with a fallback so it works before the first barometric reading arrives.
6

Filter the data down to this car

bmwdiag/mapping/registry.py · resolve()

The files were loaded at boot, before the socket existed. Now they meet the real ECU and get cut down. Three gates, then the substitution.

Three gates
  • fileDoes the ECU satisfy ecu.match? A d72-only file is skipped whole on a d71 ECU.
  • requestIs this PID in the support bitmask from stage 4? An unsupported one is dropped rather than polled forever into a refusal.
  • derivedAre all its inputs actually being read? boost disappears if map does — better than publishing a channel that can never produce a value.
Then the binding
# in the file, forever:
target: discovered_engine

# at runtime, from stage 4:
targets = {"discovered_engine": 0x12}

# every request in that file now addresses 0x12

Out of this comes a ResolvedProfile: the exact set of requests this car can answer, each bound to a real address, plus the channels they decode into.

7

Decide how often

bmwdiag/mapping/polling.py · config/modes.yaml

Every request belongs to a named polling class declaring one thing — a period in seconds — and that period follows what the channel physically does. Coolant does not move in tenths of a second; engine speed does.

ClassPeriodChannelsReasoning
motion0.1 srpm, speed, map, pedalgenuinely fast; the basis of load context
context10 sload, throttle, maf, rail, lambdacharacterises a phase, not a transient
slow10 stemps, voltage, EGRthermal mass — minutes, not seconds
rare60 sambient, baro, fuel, odometerweather and counters
dde_dyn0.5 s × 22the 22 proprietary DDE readsstaggered — see below
egs0.5 sengaged gearthe ECU that sleeps; fewer requests, fewer refusals
Stagger is the one rule that is not just a rate. The 22 DDE reads fire one per firing of the class, round-robin. So the period is the gap between firings, and a single channel refreshes every 0.5 s × 22 ≈ 11 s. Without it, all 22 multi-frame reads would land on one cycle and stall the fast channels.

A drive mode then scales those classes as a group. It is not a second scheduler — one mechanism still decides what is due.

config/modes.yaml abridged 
id: drive-modes
version: 1          # recorded with every drive

modes:
  off:
    polls: false     # connected, but sends nothing

  sampling:
    duty: {awake: 120, asleep: 600}
    exempt: [slow, rare, dde_dyn]   # these never sleep

  long:
    multipliers:
      motion: 5.0       # 0.1 s  ->  0.5 s
      egs: 4.0          # 0.5 s  ->  2 s

  normal: {}          # scales nothing, BY DEFINITION

  debug:
    multipliers:
      context: 0.01     # 10 s  ->  0.1 s
  • multiplierscales the class period. Above 1 = less often, below 1 = more often.
  • normalempty on purpose — so "what rate was this recorded at?" has exactly one answer.
  • versionchanging a multiplier changes what a recorded drive means, so the table is versioned like a mapping and travels with the data.
8

The loop

live.py · poll_loop() — runs ~10× a second, forever

Everything above happens once. This is the part that repeats.

due() Which requests have waited out their period? Returns requests, never channel names. polling.py
execute() Send them. OBD PIDs get batched into one exchange; UDS DIDs go one at a time. execute.py
decode() Bytes → numbers, following the arithmetic in the mapping. 0x0C3C ÷ 4 = 783. decoder.py
derive() Compute the channels nobody reads. boost = map − baro. derive.py
record Queue the fresh values. Only real readings — a carried-forward value is never re-logged. live.py
sleep Whatever is left of the 100 ms. live.py
One row = one real ECU reading. A slow channel keeps its last value on the dashboard between reads, but that carried-forward value is never written again. Otherwise a 60-second channel would look like it was sampled at 10 Hz.
9

When the car says no

bmwdiag/mapping/execute.py · fault_kind()

The transmission goes to sleep. Asleep, it answers a routing refusal or nothing at all. The distinction that matters is whose failure it is.

KindWhat it meansResponse
transport_nackgateway will not route to that ECU — usually asleeprecord, skip that request, carry on
transport_timeoutthe ECU did not answer in timerecord, skip, carry on
negative_responsethe ECU answered 7F with an NRC — it is there, it just does not do thisrecord with the code, skip, carry on
transport_linkthe socket itself is gonereconnect
decodebytes arrived but the mapping could not read themrecord — this is a mapping bug
late_responsethe answer to a request that had already timed out arrived — recorded under that requestdiscard, count on the request's late, carry on
unexpected_responsea frame matching nothing asked (under the pseudo-id hsfz:0x12)discard, count, trace, carry on

The last two exist because a frame is only ever accepted as the answer to a request when it fits the request: the right ECU, the positive service id, the echoed identifier (62 F3 03 for 22 F3 03, 6C 03 F3 03 for the clear), and the declared minimum length — or a 7F naming this service. Anything else is an orphan and is never returned. Where content cannot tell two answers apart (the same dynamic DID read twice), the line is given a short quiet window after a timeout before the next request goes out, a fault in a define-then-read sequence re-arms the definition, and a run of responsePending can never hold one request past an absolute deadline.

This used to be one bug. A single refusal from a sleeping transmission tore down the whole connection, and one drive recorded as four separate runs. A per-request fault now costs one request; only a genuinely dead socket costs the link — and a run of consecutive faults still triggers a reconnect, so a wedged link is not mistaken for a quiet one.

Why go to this trouble

Every arrow above could have been fifty lines of Python with the PIDs hardcoded. It was, once. Pulling the vehicle knowledge out into data buys three things that matter for a car being watched over years rather than minutes.

A new channel is a YAML edit — no code, no release. Every sample carries the version of the file that decoded it, so a dataset analysed in six months is the same dataset, not one silently reinterpreted. And nothing in the files executes, so they can eventually compile to C structures for a runtime with no Python in it at all.

Read-only throughout. The runtime can send observational diagnostic reads and nothing else — no writes, no actuators, no coding — enforced at a single choke point.
